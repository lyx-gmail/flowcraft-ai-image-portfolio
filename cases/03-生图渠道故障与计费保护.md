# 案例三：渠道 502 与「不许替用户花钱」的失败处理

## 背景

作品集生产早期，生成请求频繁失败：浏览器侧看到的是「GPT-Image 生图响应超时，请稍后重试」，服务端日志显示上游返回 HTTP 502，等待 37.96 秒，函数执行 39.69 秒（预算 300 秒）。请求编号 `a4be8a3a-9000-4c8c-b677-1fd588e2e79f`。

## 判断

先排除两类误判：

- 不是超时截断：函数还有大量预算，失败发生在 38 秒左右，且上游明确回了 502；
- 不是额度问题：额度不足会返回完全不同的提示，而这次是上游错误。

因此问题出在生图渠道链路本身。这里最重要的产品决策是：**任何失败都不自动重试**。生图是付费调用，一旦请求发出但结果未知，用户可能已经被计费；自动重试等于让用户为同一张图付两次钱。未知结果一律回报排查编号，由用户决定是否重来。

## 做法

1. 补齐安全诊断：记录上游状态码、错误码、请求编号哈希、响应类型和耗时；不记录密钥、素材和完整提示词，避免日志本身成为数据泄露面。
2. 修掉确定的不兼容项：移除上游不支持的 `response_format` 参数；保留 300 秒函数预算与 240 秒上游等待，让正常的慢渲染有机会完成。
3. 单次提交、显式失败：失败时展示「未确认，请勿重复提交」和排查编号，绝不出现「全部任务执行完毕」这类误导性成功文案。
4. 切换渠道并按同一套流程复测：在 OpenRouter 路由下先用 1K 验收，再验 2K；确认「访客额度」按预期生效、管理员白名单不受限。

## 结果

- 渠道切换后，作品集的 49 次后台生成全部一次成功（无重试），单张请求耗时 28.3–40.2 秒，中位数 33.0 秒；
- 若仍返回 502，我会停止重复生成，用诊断证据定位渠道问题——而不是用「换密钥、延长超时、重复提交」伪装成修复。

## 复盘

失败处理的本质是**替用户守住钱和数据**：宁可让用户手动重试，也不替用户做付费决定；宁可让错误可解释，也不给出模糊的成功感。这套原则后来直接复用到作品集的每一张图上：单次提交、逐张验收、失败留档不重跑。
